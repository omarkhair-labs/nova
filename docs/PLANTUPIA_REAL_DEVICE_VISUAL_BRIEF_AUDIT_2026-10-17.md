## Executive conclusion — what failed
The Android project is an actual functioning native/social/data product, not an HTML mockup. However, much of the experienced UI is still a **visual splice of Nova identity/social structures, newly added private space/care components and editorial forest/cream styling**. Code existence and green CI were incorrectly allowed to stand in for product-level visual resolution. The original brief required a distinct Plantupia experience grounded in **physical places, meaningful human care, truthful dated evidence and voluntary social knowledge**, with Nova used as an engine — not a Nova profile/feed visually left intact under plant cards.

## 02 / Important technical distinction: the disabled Add Plant
**Confirmed source pairing on this working branch:**
- Android `PlantupiaRepository.spaces()` reads `can_add_plant` with a **default of false when the key is absent**.
- Android `PlantupiaSelfServiceForms` enables `+ Add plant` only when at least one returned space has `canAddPlant=true`.
- Django `SpaceSerializer` **does** return `can_add_plant=true` for `space.owner_id == request.user.pk` or manager membership.
- The QA client still targets a legacy `240.` preview origin. An earlier on-phone QA audit saw HTML 404 from Plantupia routes; these new photos prove some routes now work, **not that the latest backend code is deployed**.

**Possible causes** (need runtime proof): stale backend serializing spaces without the field; spaces owned by another test account/shared at viewer/carer role; old account/data fixture; inconsistent environments. These are *hypotheses*, not an authorized reason to relax the server's permission model. Inspect the actual returned authorized JSON and deployed SHA; fix the real cause.

## 03 / Proposed integrated design structure, not separate skin tweaks

### My Space / Today
**Header:** wordmark + search/messages/notifications, compact personal greeting in English.  
**Attention:** one real selected review card (if any), concise due date & one reachable action.  
**Place:** photographed currently selected site *or explicitly labeled real plant-in-place image*; concise location/name and switch.  
**Plants:** recognizably photographed unit strip/grid; tap unit → real dedicated detail; quick record.  
**Evidence:** last actual dated observation only if recorded, otherwise simple empty state.  
**Secondary:** opt-in assistant and social moments further down — **not** before place, care or plants.

### Dedicated plant detail / Care / History
Plant hero (uploaded photo or honest no-cover), name/place/optional species and actor → **large tactile actual-care actions with correct custom icon family** → dated private observation timeline → next human-chosen follow-up → optional question preview. Distinct from long embedded Home subpanel. Preserve backend real persistence and privacy.

### Create, not a brochure
Tap current central **+** → clear native bottom sheet or compact selector with **Private**: `Record care`, `Add plant`, `New space`; **Public**: `Ask Circle`, `Share a moment`, `Story`; extra media formats on demand. Open Nova real editors without reimplementing social engines; avoid a hidden-only swipe requirement. A/B test if a permanent Care destination would lower task friction before changing root tabs.

### Circle / public
Plant question cards foreground question/context & human replies, not arbitrary full-bleed media for every item. The user can still publish text/video/post using retained Nova engines, but public questions must be visibly authored and linked to optional **private** observed outcomes; never expose source place or care journal by default.

### Me / profile
Compact name/avatar and profile settings → useful private plant/place dashboard on **own account only**, with correct current counts/photos → dedicated **Community** section for posts/follow graph/reels. A visitor only gets consented public identity and public community content. One coherent Plantupia palette; not a violet Nova-profile slab followed by forest-green panels.

## 04 / Research-to-redesign guardrails
- **Living Atlas:** a plant is tied to a real space, but do not fabricate aerial diagrams or architectural imagery; user-supplied photos may be test content with subjects other than plants.
- **Quiet Care:** time at plant > time scrolling. Direct user-chosen care action in first useful viewport; no pressure/streaks or auto watering assumption.
- **Field Notes:** true date, source and authored observation. No fake comparison if only one photo exists.
- **Human help:** Circle and AI are optional, not the central hero. Actual live AI provider still requires explicit staging proof.
- **Reference decomposition:** CapWords confirmed photo capture; Moonlitt content-led clarity; Day One dated photographs; Are.na linked knowledge; Focus Friend low-attention ritual. **Borrow behavior, never logos, imagery or screenshots**; awards are not proof of this implementation's UX quality.
- **Design authority:** Pass 07 is a *testable candidate*, not a final frozen mockup. Current real-device owner's rejection of the unintegrated visual composition is new evidence to guide deliberate redesign.
- **Do not conflate** finishing PR #241 with production/Play. User's target is a separate Plantupia Play app on their account after **integrated** client/device signoff.

## 05 / Finite sequence from this review to a new APK
1. **P0 functional integrity:** identify role/actual deployed `can_add_plant`; verify staging DB/social data origin and server revisions; don't add confidential customer data until isolated runtime is proven.

Sketch/interaction map must include back/keyboard and private/public before per-component Kotlin changes.

After owner visual review, iterate factual bugs and ship separate signed Play AAB only through approved distribution.
