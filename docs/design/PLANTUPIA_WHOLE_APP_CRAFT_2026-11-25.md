**Date:** 25 November 2026. **Status:** source-inventoried native candidate under implementation, with integrated build and runtime acceptance open.

## Scope and standard

The current product direction covers every exposed Android screen and its connected states, beginning with first launch, account creation and returning-user login. Creative opportunities are evaluated as changes to the real product: a more legible action, a recovered draft, a clearer permission, a meaningful illustration, or an easier return to the original task. The ambition is exceptional product craft. Awards are an aspiration, never a promised outcome or an acceptance criterion that can be established by code alone.

Plantupia keeps its own nature, architecture and lived-care identity. The existing Kotlin/Compose application, account and session ownership, Django APIs, media, messaging and safety engines remain the implementation foundation. The existing Play application identity stays unchanged. This scope does not authorize merging, deployment, database migration on a hosted service, payment changes or a store release. The independent public website and company dashboard require their own evidence; iOS remains outside this native implementation scope.

This document supplements the historical [screen closure ledger](../PLANTUPIA_SCREEN_CLOSURE_LEDGER.md), [conversion contract](../PLANTUPIA_PRODUCT_CONVERSION.md), [signature native note](PLANTUPIA_SIGNATURE_NATIVE_2026-11-25.md) and [art/journal note](PLANTUPIA_SIGNATURE_ART_AND_JOURNAL_2026-11-25.md). Older ledger references to four roots, a missing guide, or a separate profile-setup file are historical checkpoints. Current source must determine what exists today.

Parameterized destinations count once each. This count excludes embedded editors, sheets, dialogs and Activity-hosted screens.

There are **9 Activity hosts** at the application source root: MainActivity, AccountSecurityActivity, CallActivity, MessagesActivity, NotificationPreferencesActivity, PrivacyActivity, ReelsActivity, SettingsActivity and SocialGraphActivity. A host is not equivalent to one screen; for example, security, messaging and the main navigation host each contain multiple states and destinations.

## Changes made in this working increment

### Entry and form craftsmanship

Welcome uses a compact native botanical/architectural frame, clear account and login actions, a contextual delivery entry, and visible legal links. Registration presents account details followed by public identity, while using the same registration request. Login, registration and recovery share the typed email through explicit navigation. Passwords remain transient; password visibility and autofill semantics do not add new authentication providers.

Forms now include field feedback, keyboard actions, meaningful busy labels and error announcements. Recovery can return from the code stage to correct the email and invalidate stale code state. Shared buttons grow beyond their minimum height for larger text; Back controls support a disabled state. Shared loading/error/empty/retry components carry semantic information rather than relying solely on color or animation.

### Navigation and identity details

Literal corrupted question-mark navigation glyphs were replaced with the app-owned Back control in Settings, Edit Profile, visitor Profile, Create Post, Post Detail, Comments and Delivery connection. Directional settings indicators use the existing mirrored icon asset. Settings and Edit Profile content widths are bounded, auxiliary brand text yields at large text sizes, and About can scroll. Privacy and notification switches now identify the setting they control to accessibility services. Logout, legal URLs and central account ownership remain unchanged.

### Recovery of unfinished work

Shop and creation-form state are scoped to the actual login generation. The same login can restore unfinished fields after Activity recreation; a different account or fresh login begins with clean component state. Shop no longer clears already-saveable delivery fields on every first composition. Cart data, prices, accepted receipts and submission progress are still loaded from the actual source; a restored draft cannot establish order success or payment.

The space/plant creation form restores existing text, type choice and open step. It waits for the current authorized space list before validating a restored selection, and drops a selection that is no longer writable. This does not persist a new photo permission, a server acknowledgment, a public-sharing consent or an automatic save. Photo selection and pending save behavior still require lifecycle QA.

### Verification and independent web corrections

Verified presentation/branding expectations in architecture scripts were brought into agreement with actual screens, while account, transport and ownership checks remain. Executable modes on the network and people checks were restored.

The independent public website received explicit chapter passages/targets and index navigation updates, plus smoke checks that match the actual shop collection and preserved route contracts. These changes are separate from native screen acceptance. They do not make the website deployed or the Android app verified.

Its [runner](../../.github/scripts/plantupia-native-craft.sh) verifies an offline, fresh emulator with no account setup, requires the exact AndroidJUnitRunner success counts, and pulls five Compose images plus the platform keyboard image for the nominal pass and five Compose images for the narrow pass before teardown. Raw test output, configuration, diagnostics and images are retained as CI artifacts for seven days. Workflow execution and visual review are pending; configuring this gate is not a passing result. Physical-phone acceptance and the other surface groups remain separate even after these focused checks succeed.

For every group A–T, acceptance must cover the relevant normal, empty, loading, offline, error/retry, unauthorized, interrupted and acknowledged-success states. Review at 320, 360, 390 and 430 dp, large text, TalkBack, reduced motion, RTL user-authored names, keyboard-visible layouts, native Back/gesture behavior and return-to-origin continuity. Use real authorized data and media where the journey depends on them. Test 0/1/7/100-record scales, rapid navigation, new-account isolation, photo permissions, interrupted submissions, exact delivery-price rechecking, and the existing messaging/call/media functions.

A feature is ready for integrated owner review only when its source, functioning behavior and visible result agree. This document records the complete scope and the current increment; it deliberately leaves every runtime acceptance cell open until there is concrete evidence for that cell.
